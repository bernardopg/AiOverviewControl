# 2.0.0: built for DMS 2.0

This major release moves AiOverviewControl to DMS 2.0 ("Heisenberg"), the first
release from the project's new home at
[duxlabs-dev/dux-shell](https://github.com/duxlabs-dev/dux-shell). The plugin uses
the DMS 2.0 widget library directly, so it loads without a single deprecation
warning, and it now declares `requires_dms: ">=2.0.0"`. Nothing changes in what
the dashboard shows: providers, Claude profiles, remaining quota, history and
settings all carry over. Version authority remains `plugin.json`; the published
release body comes from the matching section in `CHANGELOG.md`.

## Who should upgrade

- **DMS 2.0 or newer:** upgrade. Existing settings, Claude profiles, pins and
  history keep working with no migration.
- **DMS 1.6:** stay on
  [1.22.0](https://github.com/bernardopg/AiOverviewControl/releases/tag/v1.22.0),
  the last release for DMS 1.6, until your distribution ships DMS 2.0. If you
  update anyway, DMS 1.6 reports the plugin as requiring DMS 2.0 instead of
  loading it.

Check your version with `dms version`.

## What changed for DMS 2.0

- **Widgets:** DMS 2.0 renamed its shared widgets and moved them to
  `qs.DCommon.Widgets` (`DankIcon` → `DIcon`, `DankToggle` → `DToggle`,
  `DankButton` → `DButton`, and so on). The old names still load in 2.0, but as
  wrappers that log *"… is deprecated and will be removed in a future release"*
  and name the plugin. All nine widget types the plugin used are migrated, the
  tooltip included, so the shell log stays clean and a future DMS that removes the
  wrappers will not break the plugin.
- **Reloads:** the plugin's IPC target (`dms ipc call aiOverviewControl …`) now
  registers one event-loop tick after the widget is created. On a plugin reload,
  the new widget used to register while the previous instance's handler was
  still alive: Quickshell logged that the new one would not be used, and
  destroying a handler while a duplicate is registered can crash the shell
  ([quickshell#898](https://github.com/quickshell-mirror/quickshell/issues/898)).
  This is the same deferral DMS 2.0 applies to its own plugin daemons.
- **Popout:** the dashboard's close callback is forwarded directly instead of
  through a `Binding`, which DMS 2.0 rejected with *"Unable to assign a function to
  a property of any type other than var"*.
- **Links:** the upvote button and README point to the
  [Dux Labs plugin registry](https://github.com/duxlabs-dev/dux-plugin-registry/issues/358)
  and the [plugin directory](https://duxlabs.dev/plugins). The button now reads
  **Upvote on the DMS plugin registry** in all five languages.

## Directories after the DMS upgrade

DMS 2.0 moves its directories from `DankMaterialShell` to `dms` on first start:
`~/.config/dms`, `~/.local/state/dms`, `~/.cache/dms` and `~/.local/share/dms`.
It leaves a symlink at each old path, so a plugin checkout under
`~/.config/DankMaterialShell/plugins/AiOverviewControl` keeps working and now
lives at `~/.config/dms/plugins/AiOverviewControl`. The plugin's own caches stay
in `${XDG_CACHE_HOME:-~/.cache}/AiOverviewControl/`. The docs now use the new
paths.

DMS 2.0 also changed its app ID to `dev.duxlabs.shell`. DMS rewrites the window
rules it manages itself; update any rule you wrote by hand for
`com.danklinux.dms`.

## README and project upkeep

- **Live badges:** the README shows the required DMS version straight from
  `plugin.json`, plus Security, OpenSSF Scorecard and download badges. The
  provider and language counts come from `docs/badges.json`, which
  `scripts/render-badges` derives from the settings catalog and `i18n/`. The
  metadata gate fails when the file or the README text is stale, so the numbers
  can no longer drift. The count is now the 39 providers selectable in settings.
- **Contributor credits:** the avatar grid is append-only. GitHub's API stopped
  listing [@SkippySteve](https://github.com/SkippySteve) after his commits lost
  their account link; he is now pinned, and a test fails if either README stops
  crediting him. See CONTRIBUTING.md, *Contributor credits*.
- **Signed releases:** the Sigstore provenance bundle is attached to each release
  as `.intoto.jsonl` (added retroactively to 1.22.0), so archives verify offline
  with `gh attestation verify --bundle` and OpenSSF Scorecard detects the
  signature. See [SECURITY.md](../../.github/SECURITY.md#verifying-a-release).

## Maintenance and validation

- The native UI smoke now builds against
  [DMS v2.0.0](https://github.com/duxlabs-dev/dux-shell/releases/tag/v2.0.0)
  (`duxlabs-dev/dux-shell`, with the `dux-qml-common` submodule).
- `tests/test-widget-runtime.sh` fails on any DMS deprecation warning, and also
  rejects, before starting, any type whose DMS file is a deprecation wrapper, so
  lazily loaded components are covered too.
- `scripts/qmlls-setup` finds the DMS 2.x runtime tree (`dms-shell/<hash>`) and
  never picks a stale 1.x extraction left behind by an upgrade.
- New `tests/test-render-contributors.sh` covers the append-only grid, the pinned
  contributor, excluded automation accounts and idempotent reruns.
- Verified on a live DMS 2.0.0 session on Hyprland: popout, settings, About,
  `focus`, two consecutive hot reloads and Claude profiles, with no warning or
  error from the plugin in the shell log.
- All 32 offline suites pass, along with shell syntax and shellcheck, the
  metadata, changelog and badge gates, `qmllint` against the DMS 2.0 imports,
  actionlint, zizmor, the packaging checks and the real DMS UI suite.

## Limitations

- DMS 1.6 is no longer supported; use 1.22.0 there.
- The plugin registry entry does not declare `requires_dms` yet, so the DMS 1.6
  plugin browser may still offer the update; DMS 1.6 then reports the requirement
  instead of loading the plugin.
- The new DMS 2.0 Dash tabs and overview cards are not used yet.
