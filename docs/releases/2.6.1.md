# 2.6.1: Antigravity 2.34+ local language server

A bug-fix release for Dux Shell 2.0 and 2.1. Antigravity 2.34 stopped passing
the CSRF token on its language server's command line, so the adapter could no
longer talk to the running app and silently fell back to the cloud endpoint
for every account
([#140](https://github.com/bernardopg/AiOverviewControl/issues/140),
[#141](https://github.com/bernardopg/AiOverviewControl/pull/141)). The token
is now read from the hub daemon descriptor the app writes, and the account the
app is signed in to shows the app's own quota summary again. Settings, Claude
profiles, pins and history carry over unchanged. Version authority remains
`plugin.json`; the published release body comes from the matching section in
`CHANGELOG.md`.

Thanks to [@carrotciallo](https://github.com/carrotciallo), who traced the
token to the hub daemon descriptor, documented its schema without exposing a
value, and attached a tested patch.

## Upgrading

- Requires Dux Shell 2.0 or newer; 2.1 is what CI tests. DMS 1.6 users stay
  on [1.22.0](https://github.com/bernardopg/AiOverviewControl/releases/tag/v1.22.0).
- Update through **Settings → Plugins → Check for updates**. No restart is
  needed: only the Antigravity adapter changed, and no file was added to a
  directory a running shell has already listed.
- Nothing to configure. `ANTIGRAVITY_NO_LOCAL_RPC=1` still skips the local
  server, and the new `ANTIGRAVITY_DAEMON_DIR` only matters for diagnostics.

## User-visible changes

### The running Antigravity app is read again on 2.34+

Since 2.3.0 the adapter asks the running app's language server for
`RetrieveUserQuotaSummary` over loopback Connect-RPC. That server can report
pools the cloud endpoint leaves out, and the card then shows
**Antigravity app (local language server)** as the account's sign-in method.
The server rejects calls without its CSRF token
(`401 missing CSRF token`), and the adapter found that token only in the
server's `--csrf_token` argument.

Antigravity 2.34 runs the language server as a hub daemon without that
argument. The hub writes a descriptor instead:
`~/.gemini/antigravity/daemon/hub_<httpPort>.json`, with `pid`, `httpPort`,
`httpsPort`, `lsVersion` and `csrfToken`. The adapter found no token, skipped
the server and asked the cloud endpoint. On 2.5.0 the visible symptom was the
**Gemini Models** pool vanishing from the card. On 2.6.0 the cloud
client-version fix (#133) brought that pool back, but the app's own summary
was still never used.

The adapter now finds the server in two ways:

1. **Hub descriptors (2.34+).** Each `hub_*.json` is used only if it is a
   regular file owned by the user and its `pid` is still running. A
   descriptor left behind by a crashed daemon is ignored. The descriptor's
   `httpsPort` is tried first, then the daemon's other loopback listeners.
2. **Command line (older builds).** The `--csrf_token VALUE` and
   `--csrf_token=VALUE` forms of the `…/resources/bin/language_server`
   process, as before.

The `agy` CLI hub writes a descriptor of its own and answers the same calls.
When the app and the CLI are signed in to the same account, that account's
summary is requested once.

### Privacy

The token is still handled as before. It travels in a `curl --config` pipe,
never on a command line, and never reaches the output or logs. It is sent
only to a loopback port that the descriptor's own process listens on. A
descriptor that names a port another process owns never receives the token.
TLS verification is skipped only for that loopback call, because the server's
certificate is self-signed.

## Validation and limitations

- Every shell suite, the metadata, changelog and DCO gates, and statement
  coverage (100%) pass in CI.
- New fixture cases in `tests/test-cov-b-antigravity.sh` cover a hub
  descriptor with no token on the command line, a stale descriptor whose pid
  is gone, the preferred `httpsPort` being tried first, a descriptor naming
  a port another process owns, a running daemon with no loopback listener,
  one account shared by the app and the `agy` hub, and the token never
  reaching argv or output. They fail on 2.6.0 and pass on 2.6.1.
- Checked live against Antigravity 2.35.0 with two signed-in accounts and a
  stale 2.29.0 descriptor. The app's account reads
  **Antigravity app (local language server)** (2.6.0:
  **IDE session OAuth (refreshed)**). The other account keeps its cloud
  numbers, and no account errors are reported.
- The descriptor is an undocumented internal format of Antigravity and may
  move again. The command-line path stays for that reason. If neither path
  finds a server, the adapter falls back to the cloud endpoint as before.
