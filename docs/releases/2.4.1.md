# 2.4.1: Claude Team accounts stop tripping the rate limit

A bug-fix release for Dux Shell 2.0 and 2.1. On a Claude **Team** plan, a
member's sign-in cannot read the organization's usage credits, and the plugin
asked for them again on every refresh until Anthropic rate limited the usage
endpoint that feeds the Claude card
([#123](https://github.com/bernardopg/AiOverviewControl/issues/123),
[#124](https://github.com/bernardopg/AiOverviewControl/pull/124),
[#125](https://github.com/bernardopg/AiOverviewControl/pull/125)). Settings,
Claude profiles, pins and history carry over unchanged. Version authority
remains `plugin.json`; the published release body comes from the matching
section in `CHANGELOG.md`.

Thanks to [@guidi-injenia](https://github.com/guidi-injenia), who logged every
request the adapter made on a Team account with two monitors and showed the
refused credits call repeating while the usage request itself was still served
from its cache.

## Upgrading

- Requires Dux Shell 2.0 or newer; 2.1 is what CI tests.
- Update through **Settings → Plugins → Check for updates**. No restart is
  needed: only the Claude adapter changed, and no file was added to a
  directory a running shell has already listed.
- The first refresh after the update asks for usage credits once more: a
  record written by 2.4.0 does not say which organization it belongs to.

## User-visible changes

### Refused usage credits are not asked again for a day

Usage credits (prepaid and promotional) come from
`GET /api/oauth/organizations/<org>/prepaid/credits`, which shares the
account's rate limit with `/api/oauth/usage`. A Team member who is not an
admin gets HTTP 403 there. The adapter only recorded a successful answer, so
a refusal was asked again on every run: each widget instance (Dux Shell builds
one per bar screen), each manual refresh, even while the usage request was
served from its 120 second cache. The account was soon answered HTTP 429 on
the usage endpoint, with a one hour `Retry-After`.

Every credits answer is now recorded with its time, status and organization:

- **403 or 404** (a Team member, a plan without usage credits): not asked
  again for 24 hours, and the card shows no credits.
- **429**: starts the same backoff as the usage endpoint, so neither is asked
  until it ends, honouring `Retry-After`.
- **Any other failure** (5xx, a network error, a `200` whose body is not a
  credits object): retried after the usual 10 minutes, keeping the last good
  balance.

Credits are never asked while a usage backoff holds, also when the usage
numbers come from the cache. Switching organization re-checks at once instead
of showing the previous organization's balance. The record is replaced with a
rename, so a refresh killed mid-write keeps the last one, and a corrupt, empty
or future-stamped record is checked again rather than trusted.

### The card names the next try during any pause

While a backoff holds, the card's **Updated** line shows
**Rate limited · next try HH:MM**, as 2.2.4 introduced. It now does so as well
when the pause came from the credits endpoint, and when the usage numbers
shown are a fresh snapshot from the cache.

## Validation and limitations

- Every shell suite, the QML runtime suite under the pinned Dux Shell 2.1.0,
  the metadata and changelog gates and statement coverage (100%) pass in CI.
- New fixture tests reproduce the report (four runs made four credits requests
  before the fix, one after) and cover a first refusal, a 2.4.0 record, 403
  held for a day across instances, 404, an organization switch, a 5xx and an
  HTML `200` keeping the balance, corrupt, empty and future-stamped records, a
  failed rename, and a credits 429 pausing the usage endpoint and naming the
  next try.
- Not verified against a live Team account: the fix was built from the
  reporter's request log. The 24 hour interval means a member who is made an
  admin sees the credits within a day, or at once after deleting the record.
- The backoff only spaces out this plugin's requests. The limit is per
  account: Claude Code and other tools polling the same endpoint still count.
