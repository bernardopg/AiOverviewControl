# 2.2.3: Updates load without restarting the shell

This release for DMS 2.0 fixes the plugin refusing to load after an update
made while the shell was running
([#92](https://github.com/bernardopg/AiOverviewControl/issues/92),
[#93](https://github.com/bernardopg/AiOverviewControl/pull/93)). Settings,
Claude profiles, pins and history carry over unchanged. Version authority
remains `plugin.json`; the published release body comes from the matching
section in `CHANGELOG.md`.

Thanks again to [@TMS-Namespace](https://github.com/TMS-Namespace), who
reported it right after updating to 2.2.2, with the exact error text.

## Upgrading

- Requires DMS 2.0 or newer, as 2.2.0 does. DMS 1.6 users stay on
  [1.22.0](https://github.com/bernardopg/AiOverviewControl/releases/tag/v1.22.0).
- Update through **Settings → Plugins → Check for updates**. No restart is
  needed, from any earlier version.
- If 2.2.1 or 2.2.2 left the plugin switched off with
  `BarWindows.js: File name case mismatch`, updating to 2.2.3 through the
  store loads it again. After a manual `git pull`, run
  `dms ipc call plugin-scan rescan aiOverviewControl` instead. Toggling the
  plugin on by itself is not enough while DMS still holds the failed load.
  `dms restart` always works.

## User-visible changes

### The plugin loads straight after an update

The QML engine keeps each plugin directory's file list from the first time it
loads the plugin, and DMS reuses that engine when it updates, reloads or
enables a plugin. 2.2.1 added a new module, `BarWindows.js`, next to the
widget. A shell that had loaded an older version did not see it, and Qt
reported the missing entry as `File name case mismatch`, so the plugin stayed
disabled until `dms restart`. The 2.2.1 notes asked for that restart, but an
update from the plugin store gives no such hint.

The module now lives in `lib/BarWindows.js`. A running shell has never listed
`lib/`, so it finds the file, and the plugin root holds exactly the files it
held in 2.2.0. The DankBar, the dashboard and the settings page behave as in
2.2.2.

## Maintenance

- `tests/test-hot-upgrade-layout.sh` freezes the runtime files of the plugin
  root and of `lib/` and checks that every relative import resolves. A future
  module goes into a new directory, and the rule is written down in
  `AGENTS.md`.
- `scripts/reload-plugin` also checks `lib/*.js` before reloading, and the
  reload, QML smoke, widget runtime and packaging checks include `lib/`.
- `tests/test-cov-b-9router.sh` no longer fails on the first day of a month,
  when its "yesterday" row falls into the previous month.

## Validation and limitations

- Every shell suite, the QML runtime suite under the pinned DMS, the metadata
  and changelog gates, and statement coverage pass in CI.
- Reproduced and checked on a live DMS 2.0 session (Quickshell 0.3.2, Qt
  6.12). Updating 2.2.0 to 2.2.2 in-session fails with the reported error.
  Updating that same broken session to the fix and rescanning loads the
  plugin, with the bar pills, the dashboard with live Claude data and the
  settings window all working. Updating a working 2.2.2 session reloads
  cleanly too.
- Toggling a plugin back on after a failed load reuses the cached failure,
  because DMS retries the same component URL. Store updates and
  `plugin-scan rescan` load a fresh copy. This is DMS behaviour, outside the
  plugin.
