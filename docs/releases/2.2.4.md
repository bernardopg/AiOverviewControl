# 2.2.4: Rate limits back off, stale numbers look stale, Dux Shell

A bug-fix release for Dux Shell 2.0 and 2.1 (formerly DankMaterialShell). The
Claude card stops polling Anthropic's usage endpoint while it is rate-limited,
and the bar no longer shows an old snapshot as if it were live
([#96](https://github.com/bernardopg/AiOverviewControl/issues/96),
[#97](https://github.com/bernardopg/AiOverviewControl/pull/97)). The docs and
UI strings follow the shell's new name, and the documented checkout install
copies the `lib/` directory it has needed since 2.2.3. Settings, Claude
profiles, pins and history carry over unchanged. Version authority remains
`plugin.json`; the published release body comes from the matching section in
`CHANGELOG.md`.

Thanks to [@guidi-injenia](https://github.com/guidi-injenia), who reported a
Session reading of 0% against claude.ai's 16% and then traced it to HTTP 429
from several pollers on one account, including the plugin's own instance per
monitor.

## Upgrading

- Requires Dux Shell 2.0 or newer, as 2.2.0 does; 2.1 is what CI now tests.
  DankMaterialShell 1.6 users stay on
  [1.22.0](https://github.com/bernardopg/AiOverviewControl/releases/tag/v1.22.0).
- Update through **Settings → Plugins → Check for updates**. No restart is
  needed: no file was added to a directory a running shell has already listed.
- The rename changes nothing on disk. The CLI is still `dms`, plugins still
  live in `~/.config/dms/plugins`, and the manifest key is still
  `requires_dms`. Arch's `dux-shell` package replaces `dms-shell`, and
  `dms migrate dux` (Dux Shell 2.1) moves an install off the legacy package
  repositories; neither touches plugins.
- If you installed from a checkout with the command in the 2.2.3 docs and the
  plugin did not load, copy `lib/` too, or run the corrected command in
  [Installation](../installation.md#install-from-a-checkout).

## User-visible changes

### Claude backs off a rate-limited usage endpoint

Anthropic limits `api/oauth/usage` per account, and Claude Code, other quota
widgets and status-line scripts share that limit. After a 429 the adapter
kept the last good snapshot (2.2.2 already marks it **Stale** with its real
fetch time) but asked again on every refresh. Dux Shell builds one widget per
bar screen, each with its own timer, and the 120-second cache that normally
dedupes them is never refreshed while requests fail, so a bar on several
monitors multiplied requests while the account was already limited.

Now an HTTP 429 or 5xx starts a backoff stored in the account cache, under the
lock every run already takes:

- one cache TTL (120 s) after the first failure, doubling per consecutive
  failure up to 30 minutes;
- the response's `Retry-After` (seconds or an HTTP date) when it is longer,
  capped at one hour;
- no usage or credits request until it ends, from any widget instance, a
  manual refresh or a retry; the last good snapshot is served meanwhile;
- a network failure (no HTTP status) starts none, a successful request clears
  it, and a deadline beyond the cap (the clock moved back) or a corrupt state
  file is ignored.

The card's **Updated** line adds **Rate limited · next try HH:MM** (or
**Endpoint failing** for a 5xx). Without a snapshot to show, the error names
the next attempt. [Troubleshooting](../troubleshooting.md#claude) explains how
to see the backoff and end it early.

### Stale numbers look stale on the bar

The bar pill fades a provider's percentage once its numbers are older than two
refresh intervals, the same rule as the card's **Stale** badge. Its tooltip
adds **stale since HH:MM:SS** and, during a backoff, the next try. Live
providers keep their usual colours.

### Dux Shell names

The README in English and Portuguese, the docs, the issue templates, the
manifest description and the settings and About strings in all five languages
say Dux Shell instead of DankMaterialShell, and use the shell's own names for
the bar (**Bar usage window**, **Bar pill tooltip**) and the **Dashboard**
card. Old links to `usage.md#the-dankdash-card` still resolve.

## Documentation

- The checkout install in [Installation](../installation.md) copies `lib/`;
  `scripts/check-metadata` now rejects an install command that leaves out
  `lib/`, `providers/`, `assets/`, `i18n/` or a root `.js` module. The
  first-validation commands no longer run two helpers on one line.
- The README and [Network endpoints](../usage.md#network-endpoints) said the
  plugin contacts two third-party hosts. It contacts three, each optional:
  the LiteLLM price table, Google DNS-over-HTTPS for Copilot, and the
  Frankfurter exchange-rate API (`AIOC_NO_FX=1`). The
  [security model](../security.md) now says LiteLLM prices Claude as well as
  Hermes usage, and the Portuguese README has the privacy note.
- The contributor guide lists every local gate CI runs, and the shell lint
  list in it, `AGENTS.md`, the release checklist and `ci.yml` is the same.

## Maintenance

- The native UI suite runs against Dux Shell 2.1.0 (`duxlabs-dev/dux-shell` at
  `7627111`). 2.1.0 changed `triggerHoverPopout()` and routes bar popouts
  through `PopoutManager`, but the widget only calls `triggerPopout()`, so
  `requires_dms` stays `>=2.0.0`. The pin was adopted on its publication day,
  a documented exception to the seven-day quarantine, like the 2.0.0 pin.
- CI also syntax-checks and lints `scripts/qmlls-setup`.
- `github/codeql-action/upload-sarif` 4.39.1 uploads the Scorecard results.

## Validation and limitations

- Every shell suite, the QML runtime suite under the pinned Dux Shell 2.1.0
  (pointer pass included), the metadata and changelog gates and statement
  coverage pass in CI.
- New fixture tests cover the backoff (first delay, doubling, cap,
  `Retry-After` in seconds and as a date, absurd and over-cap values, clock
  skew, network failures, corrupt state, the error text without a snapshot,
  and that skipped runs send no request), and a widget runtime step covers
  the faded pill, the tooltip and the card's backoff text.
- The backoff only spaces out this plugin's requests. The limit is per
  account: if Claude Code or another tool keeps polling, the endpoint can stay
  limited, and the card keeps the last good snapshot marked **Stale**.
- The README screenshots were not retaken: the settings window still shows
  1.16.2 with the DankBar labels.
